# Wazuh–n8n Security Alert Automation

A SOC-focused security automation lab that integrates **Wazuh** with **n8n** using a custom webhook-based integration. The workflow receives Wazuh alerts, normalizes and classifies them by severity, applies risk-based triage logic, and automatically sends email notifications for alerts that require analyst attention.

The project was built as a practical **SOC automation / SOAR-style lab** with additional emphasis on **auditability, controlled escalation, evidence retention, and change management**.

---

## Project Objective

The objective was to build a functional Wazuh–n8n integration that:

- Receives Wazuh alerts in n8n through a webhook.
- Processes and normalizes alert data.
- Classifies alerts according to Wazuh severity.
- Applies conditional SOC triage logic.
- Escalates relevant alerts through email.
- Avoids unnecessary escalation of low-severity events.
- Produces reproducible technical evidence for validation and audit purposes.

## Unique Automation Use Case

### Risk-Based Wazuh Alert Triage and Email Escalation

Instead of forwarding every Wazuh alert directly to an analyst, the n8n workflow performs an initial triage step.

The workflow extracts fields such as:

- Rule ID
- Wazuh severity level
- Rule description
- Agent ID
- Agent name
- Source IP
- Destination user
- Manager name
- Timestamp

The workflow then assigns:

- Severity
- SOC priority
- Automated action
- Notification requirement

This allows the workflow to distinguish routine alerts from alerts that require human review.

---

## Risk Classification Logic

| Wazuh Level | Severity | Priority | Automated Action | Notification |
|---:|---|---|---|---|
| 0–6 | LOW | P4 | `LOG_ONLY` | No |
| 7–9 | MEDIUM | P3 | `ANALYST_REVIEW` | Yes |
| 10–11 | HIGH | P2 | `SOC_ESCALATION` | Yes |
| 12+ | CRITICAL | P1 | `IMMEDIATE_SOC_ESCALATION` | Yes |

The severity mapping is used for **workflow triage**, not as a declaration that an event is automatically a confirmed incident.

- Method: `POST`
- Path: `wazuh-alert`
- Production endpoint:

```text
http://<N8N-HOST>:5678/webhook/wazuh-alert
```

The Wazuh integration sends JSON alerts to this endpoint.

## Wazuh Integration

The Wazuh Manager uses a custom integration named:

```text
custom-n8n
```

The integration consists of two files:

```text
/var/ossec/integrations/custom-n8n
/var/ossec/integrations/custom-n8n.py
```

### Wazuh Configuration

The following integration block was added to `ossec.conf`:

```xml
<ossec_config>
  <integration>
    <name>custom-n8n</name>
    <level>5</level>
    <alert_format>json</alert_format>
  </integration>
</ossec_config>
```

This causes Wazuh alerts at level 5 or higher to be passed to the custom integration.

## Custom Integration Flow

```text
Wazuh Alert
    |
    v
Temporary Wazuh Alert JSON
    |
    v
custom-n8n Shell Launcher
    |
    v
custom-n8n.py
    |
    v
HTTP POST
    |
    v
n8n Webhook
```

The Python script:

1. Reads the alert file generated by Wazuh.
2. Serializes the alert as JSON.
3. Sends the alert to the n8n production webhook.
4. Records integration success or failure in:

```text
/var/ossec/logs/integrations.log
```

Example successful delivery:

```text
custom-n8n: SUCCESS - HTTP 200 | Rule ID: 100100 | Level: 10 | Agent: wazuh-manager
```

## Troubleshooting Performed

During implementation, the integration initially attempted to read the wrong command-line argument:

```text
> /dev/null 2>&1
```

The original code used:

```python
alert_file = sys.argv[-1]
```

The issue was identified using the Wazuh integration logs and corrected to:

```python
alert_file = sys.argv[1]
```

This restored correct processing of the Wazuh temporary alert file.

A temporary network error was also observed during testing:

```text
No route to host
```

Connectivity was revalidated between the Wazuh VM and the Windows host running n8n before continuing.

## Security and Governance Considerations

The implementation was designed with several operational and governance controls in mind.

### Change Control

A backup of the Wazuh configuration was created before modifying `ossec.conf`.

```text
ossec.conf.task8-backup
```

### Least Privilege

Custom integration files were assigned controlled permissions:

```text
root:wazuh
-rwxr-x---
```

### Auditability

Integration execution results are recorded in:

```text
/var/ossec/logs/integrations.log
```

This provides evidence of successful or failed forwarding attempts.

### Risk-Based Escalation

Low-severity events are not automatically escalated. Higher-severity events are prioritized for analyst review.

### Human-in-the-Loop Response

The workflow deliberately avoids automatically blocking IP addresses, disabling accounts, or performing destructive containment based only on alert severity.

This reduces the risk of:

- false-positive containment
- service disruption
- accidental account lockout
- inappropriate automated response

### Evidence Retention

Screenshots, configuration fragments, workflow exports, logs, and test results are retained as implementation evidence.

## Stopping the Lab

To stop n8n without deleting workflows or credentials:

```powershell
docker stop wazuh-n8n
```

The persistent Docker volume retains the n8n configuration.

Do **not** remove the `n8n_data` volume unless the environment is intentionally being rebuilt.
